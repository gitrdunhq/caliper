| PERF-002 | high | src/caliper/plugins/trivy.py | 131 | N+1 file I/O: Same issue as PERF-001 — classify_dependency_kind() is called once per finding in a loop over vulnerabilities/packages, causing repeated filesystem reads of the same manifest and lockfiles. | Apply the same caching strategy as PERF-001: cache manifest/lockfile contents at scanner initialization, indexed by manifest path, and reuse across all package classifications in a single scan. |
| PERF-003 | medium | src/caliper/core/manifest_discovery.py | 352 | Regex recompilation: _appears_in_lockfile() compiles a new regex pattern on every call, even though Python's re module caches compiled patterns. The dynamic package_name in the pattern means each unique name triggers a new compilation. For manifests with many packages, this creates hundreds of regex compilations. | Use functools.lru_cache to memoize compiled regex patterns by package_name, or consider using a simpler substring match approach if word-boundary precision can be relaxed. |
| CORR-001 | high | src/caliper/plugins/trivy.py | 130 | For trivy findings, `manifest_path` is built from Trivy's `Target` field, which for lockfile-based ecosystems (npm/yarn/pnpm, Cargo, Go modules, Poetry) is the *lockfile* itself (e.g. `package-lock.json`, `Cargo.lock`, `poetry.lock`, `go.sum`), not the manifest. `classify_dependency_kind()` only recognizes manifest filenames (`pyproject.toml`, `package.json`, `pom.xml`, `go.mod`, `Cargo.toml`, `requirements*.txt`) via `_resolve_direct_parser`/`_MANIFEST_TO_LOCKFILES` (manifest_discovery.py:341-347, 390). Passing a lockfile filename as `manifest_path` means `_resolve_direct_parser` returns None (no parser matches a lockfile filename) and `_MANIFEST_TO_LOCKFILES.get(filename)` also misses (its keys are manifest names, not lockfile names), so the function always falls through to `unknown`. | Map the trivy `Target`/lockfile filename back to its owning manifest filename (invert `LOCKFILE_MAP`) before calling `classify_dependency_kind`, or extend `classify_dependency_kind` to accept a lockfile path directly (locate the sibling manifest via `LOCKFILE_MAP` when `manifest_path.name` is a known lockfile). |
| CORR-002 | medium | src/caliper/core/review_summary.py | 171 | The module docstring/`summarize_review` docstring state a below-floor semgrep finding is 'still counted (as a note)' and 'never affect[s] blocking_count/verdict either way' (lines 148-155). But the error/warning/note counting loop at line 171 iterates over the raw, unfiltered `results` (not `scored_results`/the floor-filtered set), classifying each finding's level purely from `level_for(severity)`. When `semgrep_min_severity` is configured above the default "medium" (e.g. "high", via `thresholds.semgrep.min_severity` in repo_config.py), a below-floor "medium"-severity semgrep finding maps to level "warning" (SEVERITY_TO_LEVEL), not "note", so it is counted in `warning_count` and can flip the verdict from `clear` to `warnings` — contradicting the documented invariant that below-floor findings never move the verdict. | Run the counting loop over `scored_results` (the floor-filtered list) instead of raw `results`, or explicitly reclassify below-floor findings to the "note" level before counting, so counts/verdict match the documented contract for any configured `semgrep_min_severity`, not just the default "medium". |
| CORR-003 | low | src/caliper/core/manifest_discovery.py | 398 | `classify_dependency_kind`'s direct-dependency check normalizes both the target package name and declared names via `_normalize_dep_name` (lowercase, `_`->`-`) before comparing (lines 386-388), but the transitive/lockfile check at line 398 passes the raw, unnormalized `package_name` into `_appears_in_lockfile`, which does an exact-case, exact-punctuation regex match against the lockfile text. | Normalize `package_name` (and ideally the lockfile line's package token) the same way as the direct-dependency comparison before running the regex search, or match on `_normalize_dep_name(package_name)` against a normalized token stream instead of raw substring search. |
